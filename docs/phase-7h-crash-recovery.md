# Phase 7H — Crash Recovery & Persistence Validation

## 現状確認

作業開始時にGit状態、Phase 7Gのコード・テスト・設計文書を確認した。
対象ディレクトリと祖先に適用されるAGENTS.mdは見つからなかった。
既存テストは依頼文の82件ではなく実測80件（library 73、binary 7）。
既存差分と未追跡のPhase 7F・7G資料、調査資料を保持した。

保存方式はrequests.journalへの追記とsync_all。
一時ファイル、保存時のrename、明示的flushは存在しない。
従来の再起動試験は主に同一プロセスでdrop/openするものだった。
今回は実際のプロセス強制終了、別プロセスによる再読み込み、
ロック解放、正常な既存履歴の保全を追加検証した。

## 試験方式

src/pre_sign/lifecycle/persistent.rsにcfg(test)限定の停止点を追加した。
通常ビルドの保存処理・安全条件は変更していない。
JSON途中の試験だけ書き込みを半分で分割し、停止位置を確定する。

src/pre_sign/lifecycle/persistent/tests/crash.rsは新規作成した一時ディレクトリ
だけを所有する。独立した子テストプロセスが停止点到達を通知し、
親はそのChildハンドルだけをkillする。終了signalが9（SIGKILL）であることを検査。
タイムアウトと子プロセス回収を備え、再読み込みも別の子プロセスで行う。
停止点での待機をSIGKILLする試験であり、カーネル内sync実行中の停止ではない。

既存のモックRPC・メモリ内合成鍵・署名応答fixtureを再利用する。
実ウォレットや本番保存先にアクセスしない。
子プロセスのstdout/stderrは破棄し、秘密情報をログに出さない。

## 実際の強制終了：7シナリオ

| 状態・停止点 | 再起動後 |
| --- | --- |
| PROCESSING_RESPONSE書き込み前 | AWAITING_SIGNATUREを復元、ID再利用拒否 |
| PROCESSING_RESPONSEのJSON半分を書き込み後 | 不完全JSONとしてストア全体の読み込み拒否 |
| PROCESSING_RESPONSE書き込み後・sync前 | PROCESSING_RESPONSE復元、ID再利用拒否 |
| PROCESSING_RESPONSEのsync成功直後 | PROCESSING_RESPONSE復元、ID再利用拒否 |
| SIGNEDのJSON半分を書き込み後 | 不完全JSONとして拒否 |
| SIGNEDのsync成功直後・呼び出し元への返却前 | SIGNED復元、ID再利用拒否 |
| VALIDATINGのsync成功直後 | VALIDATING復元、ID再利用拒否 |

各シナリオで既存のbaselineレコードのバイト列が保存ファイルの先頭に
そのまま残ることを確認。再読み込み前後で全ファイルが不変であることも検査。
正常復元時は同一ID・異なるメッセージへのID流用の両方を拒否する。
破損時の「復旧」は自動修復ではなく安全側の停止を意味する。

sync前のデータが再読み込みできたのは、プロセス終了でOSのページキャッシュが
失われない今回の環境での結果。電源断時の永続性を意味しない。

## 保存失敗・再起動：3シナリオ

- 子プロセス内で書き込みハンドルを読み取り専用に交換し、実writeエラーを発生。
  応答処理と再試行が失敗し、ストアがpoisonされることを検査。
  別プロセスでAWAITING_SIGNATUREを復元しても再登録不可。
  これはI/O障害注入試験でありSIGKILL試験ではない。
- 一時領域内のジャーナルを別名に退避して欠損を作り、別プロセスで拒否を確認。
  元データは退避先に完全保持され、自動再作成されない。
  このrenameは欠損の試験操作であり製品の保存方式ではない。
- 保存ファイルを0644にして、別プロセスで拒否を確認。内容は不変。

## 結果

追加10シナリオ＋子プロセス実行用テスト入口1件＝新規11件。
既存80件を含め91件成功、0件失敗（library 84、binary 7）。
子プロセス入口は環境指定がない通常実行では何もせず戻るため、
独立した検証シナリオとしては数えない。
cargo fmt --check、cargo check --offline --locked、
cargo test --offline --locked、git diff --checkが成功。
proc-macro-error2の既存の将来互換性警告は残る。

今回の範囲で製品コードの新規不具合は検出しなかった。
不完全な追記があると正常な過去レコードも含めストアを利用できなくなるが、
これはPhase 7Gの安全側停止方針であり、自動切り詰めで回避していない。
