## 診断と変更

StateStore::open_diagnosedを追加し、既存openも同じローダーを利用する。
Diagnosticは異常分類、固定の発生箇所、レコード行番号、
復旧可能性、停止理由、手動確認事項を返す。
復旧可能性は「自動復旧不可・履歴完全性確認まで再開禁止」とする。
原文、実パス、要求ID、JSON解析器のエラー本文を保持・表示しない。
通常エラーとDebug表示の両方で入力中の機密情報を露出しないことをテストした。
診断APIは読み込みと排他ロックのみで、内容を変更しない。
CLIコマンドとしては未接続。成功時はStateStoreとしてロックを保持する。

既存serdeエラーは未知フィールド名などの入力値を含む可能性があった。
これを固定分類に置き換えた。既存ローダーが無視していた余分なファイルも
UnexpectedArtifactとして拒否する。保存専用ディレクトリにはjournalだけを置く。
一時ファイルの内容を比較して新しい方を選ぶ処理は追加しない。
既存の状態遷移・チェックサム・ID再登録拒否は再利用した。

| 異常 | 診断分類・挙動 |
| --- | --- |
| JSON構文破損 | JsonSyntax、停止 |
| JSON途中切断、終端改行欠落 | Truncated、停止 |
| 必須フィールド欠落、未知フィールド・状態名・型不正 | Fields、停止 |
| 不正な状態遷移・レコード条件 | InvalidState、停止 |
| 同じIDのCREATED再登録 | DuplicateRegistration、停止 |
| 未知ヘッダー/schema | HeaderOrSchema、停止 |
| 未知protocol_version | ProtocolVersion、停止 |
| チェックサム・連結不一致 | Integrity、停止 |
| ファイル/ディレクトリ権限または型不正 | PermissionsOrType、停止 |
| journal/ディレクトリ欠損 | Missing、停止、自動作成なし |
| 一時ファイル等の余分な項目 | UnexpectedArtifact、内容に関係なく停止 |
| ロック取得失敗、読み込み失敗、容量超過 | LockUnavailable / Access / Size、停止 |

同じIDが複数行に登場すること自体は正常な状態遷移でも起こる。
禁止するのは再登録・不正遷移・識別情報変更である。

## 手動復旧手順（今回は実施しない）

1. **停止する。** 関係するアプリケーションと署名要求の生成・応答受付を停止する。
   全利用プロセスを特定し、オペレーターが通常の停止手順で止める。
   ロックを無視した操作・自動再起動・ID変更による再試行はしない。
   原因不明のプロセスを無差別に終了しない。

2. **原本を保全する。** JSONを画面やログに表示せず、原本を編集・切り詰め・
   rename・削除・初期化しない。停止済みで書き込みがないことを確認する。
   元パス、所有者、権限、サイズ、更新日時、取得時刻をアクセス制限した記録へ残す。
   パスやファイル名にも機密情報があり得るため共有ログには載せない。

3. **権限を保持したバックアップを作る。** 保存ディレクトリの外に、
   アクセスを限定した0700の新規保全ディレクトリを作る。
   承認済みの管理者が、上書きしない新規宛先へGNU cpの
   --archive --preserve=all相当でディレクトリ全体をコピーする。
   シンボリックリンクは追跡せず、ACL・所有者・拡張属性も確認する。
   コピーに失敗した場合は保全成功としない。広すぎる元権限は原本で変更せず、
   外側の0700ディレクトリで保護する。
   書き込み停止を維持したまま原本とコピーのサイズ・SHA-256を比較する。
   本文は出力しない。ハッシュとメタデータも限定保管し、公開しない。
   ファイルシステムの読み取りでatimeが変わる可能性があるため、
   厳密な証拠保全が必要なら管理者による読み取り専用スナップショットを使う。

4. **コピーで原因を調べる。** 固定分類と行番号を用いて、
   不完全書き込み、権限変更、所有者変更、余分な項目、外部編集、
   バックアップ巻き戻しの可能性を確認する。
   一時ファイルは正本として採用しない。JSON本文を外部サービスへ渡さない。
   原本・保全コピーを作業用のアプリケーションへ接続しない。

5. **復旧可否を判断する。**
   - 権限や競合だけが原因でも、履歴が完全で改変されていない根拠が必要。
     修正は別途承認された手順で行い、今回の診断から自動修正しない。
   - JSON破損、欠損、重複、不正遷移、未知versionは原則再開不可。
     完全かつ最新の履歴を外部証拠と照合できなければ安全な復旧を証明できない。
   - 古いバックアップの復元や末尾切り詰めでパーサーが通っても、
     使用済みIDが失われる可能性がある。読み込み成功だけを復旧成功としない。
   - 残存一時ファイルを退避するだけでも別途承認を必要とし、
     出所・正本との関係を解明するまで運用再開しない。

6. **復旧後の確認（別途承認された場合のみ）。**
   正式な形式、権限・所有者、排他ロック、履歴完全性、使用済みIDの網羅、
   全利用者が同じ保存先を使用することを確認する。
   検証はまず隔離コピーで実施し、既存IDの再登録拒否を確認する。
   処理途中・SIGNED・REJECTED・EXPIREDの要求は再開しない。
   実署名・送信はこの復旧手順の範囲外。

7. **再開禁止条件。** 履歴欠損の可能性、最新性不明、改ざんの疑い、
   ロック競合、原因未特定、バックアップ不一致、未知schema、
   未検証の移行処理がある場合は停止を維持する。
   新しい保存先や要求IDを作ることを復旧の代用にしない。

## 初回起動と喪失の区別・残るリスク

openは欠損を常に拒否。initializeは明示的な初回作成で既存ディレクトリを拒否する。
ただし保存先全体が消えた場合、正常な初回と過去履歴喪失は区別できない。
外部の信頼できる登録情報なしに「初回」と安全に断定できない。
今回initializeの自動呼び出しや自動復旧は追加していない。

正常なレコード境界への切り詰め、バックアップ巻き戻し、同一ユーザーの
悪意あるパス差し替え・ファイル変更、別ストアの利用は依然保証対象外。
ディレクトリ走査とopenの間の敵対的競合への完全耐性はない。
実電源断、実syncエラー、NFS、復旧操作の実地検証は未検証。
診断結果は最初の異常のみを返し、他の異常がないことを保証しない。
